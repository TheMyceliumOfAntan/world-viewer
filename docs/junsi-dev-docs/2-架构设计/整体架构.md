# 整体架构

## 1. 定位

World Viewer 是一个 Minecraft 存档可视化工具。读取存档的 Anvil region 文件，按需渲染成地图瓦片，在桌面窗口中浏览。设计目标是支持**模组化存档**（尤其 GTNH 这类 1.7.10 + NotEnoughIDs 的重度模组整合包）以及**跨 MC 版本**的存档格式。

技术栈：Tauri 2（Rust 后端 + React 前端 + WebView2 渲染）。

## 3. 关键设计决策

### 3.1 按需瓦片而非预渲染
打开存档立即出图，平移缩放时按需请求。每个瓦片 256×256，zoom 0 覆盖 16×16 区块（1 像素 = 1 方块），zoom 4 覆盖 1 区块（16 像素 = 1 方块）。

### 3.2 瓦片级表面缓冲（而非区块级）
渲染以整个瓦片为单位构建 `Surface`（含 1 格边距 + 1 区块边距），再统一做浮雕着色。这样跨区块的坡度比较正确，且消除区块接缝。详见 `2-架构设计/渲染管线.md`。

### 3.3 方块标识与显示名分离
`color_ref()` 只返回规范方块 id 名（如 `minecraft:grass`），显示名由 `display_name()` 单独提供。渲染器依赖 id 名做染色分类，混用会导致染色静默失效。详见 `1-决策记录/ADR-001`。

### 3.5 生物群系染色区分"未染色"与"已着色"
调色板对草/树叶存的是未染色灰度色，对水/芦苇存的是最终色。前者乘 tint 上色，后者按平原基准做比例缩放，否则水会被二次压暗成近黑。详见 `1-决策记录/ADR-004`。

### 3.6 水面/水底双缓冲
列扫描遇到水时继续下钻取水底，按深度混合水色与水底色（浅水透底、深水回归水色）。详见 `2-架构设计/渲染管线.md` §9.1。

### 3.4 瓦片 URL 携带世界标识
瓦片 URL 形如 `http://tile.localhost/{worldKey}/{dim}/{z}/{x}/{y}.png?ymax=N&water=1&shade=1&alt=1`。`worldKey` 由存档路径哈希得到，后端忽略该段，仅用于隔离浏览器缓存与前端缓存，避免切换存档后复用旧瓦片。`water`/`shade`/`alt` 为渲染开关（缺省全开），详见 `3-API规范` §3.1。

## 4. 数据流

```
用户点击"加载存档"
   │
   ├─► invoke("open_world", { path })
   │      world::open_world()
   │        ├─ 读取 level.dat → 存档名 / 玩家位置 / 世界种子
   │        ├─ 探测实例根（向上找 journeymap/ 或 mods/）
   │        ├─ 加载 Palette（JM 调色板 + level.dat 方块表 + 内置表）
   │        ├─ 扫描维度（region/ 与 DIM*/region/，仅保留有数据的）
   │        └─ 加载路径点（JourneyMap / Xaero / VoxelMap）
   │      → 返回 WorldInfo
   │
   └─► 前端设置瓦片 URL 模板，Leaflet 请求可见瓦片
          │
          └─► tile://{worldKey}/{dim}/{z}/{x}/{y}.png?ymax=N&water&shade&alt
                 （协议处理器在独立线程中）
                 render::render_tile()
                   ├─ 批量并行加载所需区块（含边距）
                   ├─ 逐列扫描 Surface（颜色 + 高度 + 水底）
                   │    └─ 读 biome（1.18+ 逐 section / 1.7–1.17 chunk 级）
                   ├─ 水面按深度混合水底颜色
                   ├─ 浮雕着色（hillshade）
                   ├─ 降采样到 256×256
                   └─ PNG 编码
                 → 响应体 = PNG，响应头 X-Tile-Empty 标记"无数据"
```

`level.dat` 只读一次即可取全三项：存档名（`Data.LevelName`）、玩家位置（`Data.Player`）、世界种子（`Data.WorldGenSettings.seed`，旧版为 `Data.RandomSeed`）。种子以字符串序列化，避免 `i64` 超出 JS 安全整数范围时精度丢失。

## 5. 并发模型

| 位置 | 机制 | 原因 |
|------|------|------|
| 协议处理器 | `std::thread::spawn` | 渲染不能阻塞 Tauri 事件循环，否则平移缩放时窗口卡顿 |
| 区块加载 | `std::thread::scope` 分片 | 单瓦片需 324 个区块，串行读取耗时约 700ms |
| 全局状态 | `Mutex<Option<...>>` | 同一时刻只打开一个存档，锁竞争可忽略 |
| 前端瓦片请求 | 并发上限 6 + 队列 | 避免一次性发出上百个请求 |

## 6. 性能基线

实测于 GTNH 2.8.4 存档（主世界 8 个 region，18MB）：

| 操作 | 优化前 | 优化后 |
|------|--------|--------|
| 单区块加载+解析 | 2.14 ms | 0.33 ms（定向解析 4.4x） |
| zoom 0 瓦片（324 区块） | 710 ms | 139.5 ms |
| 一屏 16 瓦片 | 4190 ms | 1055 ms |
| 主线程 long task | — | 0 个 |
